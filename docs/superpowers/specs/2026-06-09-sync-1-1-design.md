# Sync 1.1 Design

## Context

Shrike is a Rust atproto library modeled after atmos. Atmos PR #1, "Sync 1.1 Support", implemented a full verifier and streaming integration around the current atproto sync specification and the Bluesky sync iteration proposal:

- atmos PR #1: https://github.com/jcalabro/atmos/pull/1
- atproto sync spec: https://atproto.com/specs/sync
- sync iteration proposal: https://github.com/bluesky-social/proposals/tree/main/0006-sync-iteration

The relevant atmos merge commit is `c55ad5f731fc577e8be1cbf577c36d42f1fbd42f`, merged on May 22, 2026. Later atmos commits after that merge include user-agent fixes, Jetstream v2 cursor support, MST remove/height fixes, and JSON tags for verifier state. None of those later commits change the core sync 1.1 verifier model, but the MST fixes and state serialization behavior should be reflected in shrike tests.

Shrike already has most low-level pieces: syntax types, v3 commit encode/decode/sign/verify, CAR, MST, identity resolution, XRPC, generated sync lexicon types, and a streaming client. The missing piece is the verifier/state machine. Today `#sync` is skipped and `#commit` operations are trusted from the envelope/CAR parse instead of being verified against signed commit state.

## Goal

Implement full sync 1.1 support in shrike in one feature branch, split into small TDD commits. The implementation should be Rust-native, robust against untrusted upstream firehose and `getRepo` data, and preserve shrike's existing no-verifier streaming behavior.

## Architecture

Add a `sync::verifier` subsystem with:

- Raw sync event structs that preserve every verification-relevant field from `com.atproto.sync.subscribeRepos`: commit CID, CAR bytes, `prevData`, op `prev`, `#sync` blocks, `seq`, `rev`, `time`, account status, and account active flag.
- An async `StateStore` trait that callers can back with their own database. Shrike will provide only a `MemStateStore` for tests and development.
- A `Verifier` that owns per-DID serialization, state access, identity resolution, policies, stats, resync rate limiting, async resync workers, per-DID pending queues, and async result/error delivery.
- Streaming integration that can run with or without a verifier. With a verifier, the stream yields verified operations and resync operations while preserving same-DID FIFO ordering and allowing cross-DID parallelism.
- A keyed scheduler for parallel streaming verification. The scheduler should be small and generic enough to test independently, but not exposed as a broad public abstraction unless needed.

The verifier is responsible for correctness. The persistence layer is responsible only for durable storage of state. This keeps database choice with callers and avoids pulling large storage dependencies into shrike.

## State Store

The storage trait should be async and narrow:

```rust
#[async_trait::async_trait]
pub trait StateStore: Send + Sync {
    async fn load_chain(&self, did: &Did) -> Result<Option<ChainState>, SyncError>;
    async fn save_chain(&self, did: &Did, state: ChainState) -> Result<(), SyncError>;

    async fn load_hosting(&self, did: &Did) -> Result<Option<HostingState>, SyncError>;
    async fn save_hosting(&self, did: &Did, state: HostingState) -> Result<(), SyncError>;

    async fn delete(&self, did: &Did) -> Result<(), SyncError>;
}
```

`ChainState` stores the last accepted repo revision and MST root CID for a DID. `HostingState` stores the latest account hosting event state: active flag, optional status string, source sequence number, and event time string.

`MemStateStore` should use Tokio-safe synchronization and be documented as non-durable. It is appropriate for tests, examples, and short-lived tools, not production consumers that need replay safety across restarts.

## Policies And Errors

Policies should be Rust enums with explicit defaults:

- `VerifierPolicy::Resync` default: chain breaks and inversion failures queue async resync.
- `VerifierPolicy::Error`: typed errors are returned. If the new commit's data CID is trustworthy enough, state advances to prevent repeated reports of the same bad event.
- `HostingPolicy::Track` default: persist account hosting state, but do not gate commit/sync events.
- `HostingPolicy::Gate`: reject commit/sync events for non-active DIDs.
- `LegacyCommitPolicy::Accept` default: accept Sync 1.0-shaped commits after signature and op-CID checks, and count them.
- `LegacyCommitPolicy::Reject`: route legacy commits through verifier policy.
- `LenientInversion` default true: when `prevData` matches local state but local inversion produces a different root because the CAR is inversion-incomplete, accept the commit while surfacing an `InversionIncomplete` signal.

Typed errors should include:

- `ChainBreak`
- `Inversion`
- `InversionIncomplete`
- `Signature`
- `FieldMismatch`
- `FutureRev`
- `CommitTooLarge`
- `DuplicatePath`
- `OpCidMismatch`
- `ResyncFailed`
- `ResyncRateLimited`
- `AccountInactive`
- `RevRegression`
- `BufferOverflow`

Stats should be atomic counters exposed via a snapshot struct. Include counters for verified events, chain breaks, inversion failures, lenient inversion accepts, signature failures, resyncs, resync failures, replay drops, future rev rejections, field mismatches, op-CID mismatches, legacy commits, missing record blocks, duplicate paths, oversized commits, sync no-ops, inactive-account drops, account replay drops, and state-save failures.

## Commit Verification Flow

`Verifier::verify_commit` should:

1. Parse and preserve the full raw event.
2. Reject future revs before per-DID locking.
3. Reject oversized commits before per-DID locking: `blocks <= 2_000_000`, `ops <= 200`.
4. Acquire the per-DID lock.
5. Apply hosting gate if configured.
6. Load chain state and silently drop rev replays.
7. Reject duplicate op paths.
8. Decode the CAR once into a temporary block store and decode the signed inner commit.
9. Verify CAR root equals envelope commit CID.
10. Detect legacy Sync 1.0-shaped commits and apply the configured policy.
11. For non-first-sighting, non-legacy events, invert ops against the post-state MST and compare both the inverted root and `prevData` to persisted `ChainState.data`.
12. Verify envelope fields match the inner commit: DID, rev, and version 3.
13. Resolve identity, verify the commit signature, and purge/refresh identity once on signature failure.
14. Check each op CID against the post-state MST.
15. Build verified operations, save new chain state, and increment stats.

This order is based on atmos' actual `VerifyCommit` implementation. Atmos' comment summary lists rev replay before hosting gate, but the actual implementation applies hosting gate before chain load/replay. Shrike should follow the implementation behavior.

## Sync Verification Flow

`Verifier::verify_sync` should:

1. Parse and preserve the full raw event.
2. Reject future revs.
3. Acquire the per-DID lock.
4. Apply hosting gate if configured.
5. Load chain state and silently drop rev replays.
6. If the embedded commit decodes and its `data` equals stored `ChainState.data`, validate envelope/inner fields and signature, then advance rev without fetching the full repo.
7. Otherwise run resync through `getRepo`.

The atmos implementation performs the `#sync` resync synchronously after these checks. Shrike should mirror that initially unless implementation evidence shows it creates unacceptable streaming backpressure; if that happens, change the design deliberately rather than silently changing semantics.

## Account Event Flow

`Verifier::on_account_event` should:

1. Acquire the per-DID lock.
2. Drop account replays by sequence number.
3. Persist `HostingState { active, status, seq, time }`.
4. Fire an optional account-state callback or expose the state transition through observable results/stats.

The per-DID lock must serialize account state changes against commit and sync hosting gates.

## Resync Flow

Resync should:

1. Apply hosting gate if configured.
2. Apply per-DID resync rate limiting.
3. Fetch the full repository through `com.atproto.sync.getRepo`.
4. Parse the returned CAR and decode the root commit.
5. Verify the fetched commit signature.
6. Verify fetched commit invariants: version 3, DID matches request, and rev does not regress or contradict existing state at equal rev.
7. Walk the MST and produce resync operations for all records.
8. Save chain state to the fetched commit's `(rev, data)`.
9. Emit a resync result and update stats.

Async resync workers should process chain-break-driven resyncs. While a resync is in flight for a DID, new same-DID commits should be buffered up to a bounded capacity. Overflow must surface `BufferOverflow`; it must not silently drop data. After the resync succeeds, the worker replays pending commits under the same per-DID lock and emits one combined resync result.

## Streaming Integration

Without a verifier, `streaming::Client` behavior stays compatible with current shrike.

With a verifier:

- `#account` events call `Verifier::on_account_event` before being emitted.
- `#commit` events call `Verifier::verify_commit`; verified operations replace lossy parsed operations.
- `#sync` events call `Verifier::verify_sync`; no-op syncs are dropped and resync operations are emitted.
- Async resync completions and async worker errors are drained alongside WebSocket reads.
- Same-DID events are processed FIFO.
- Different DIDs can verify concurrently.
- Cursor advances by watermark, not by last yielded event, so restart after parallel verification does not skip in-flight lower sequence events.
- Per-DID queue overflow surfaces a typed error.
- `parallelism = 1` preserves serial global behavior for tests and conservative callers.

## Robustness Requirements

The firehose and `getRepo` responses are untrusted input. The implementation must treat all upstream bytes as hostile or malformed until verified.

The verifier should reject or surface typed errors for malformed CBOR, truncated CARs, CAR roots that do not match the envelope, missing commit blocks, mismatched envelope fields, oversized `blocks`, too many ops, duplicate paths, missing `prev` CIDs where inversion requires them, invalid op CIDs, op CIDs inconsistent with the post-state MST, future revs, rev replays, bad signatures, identity refresh failures, hosting gate failures, resync rate limits, resync rev regression, and store save/load failures.

Silent fallback is not acceptable for integrity-relevant failures. The only silent drops should be deliberate replay/no-op cases with counters where appropriate.

## Test Strategy

Tests must be broad, adversarial, deterministic, and fast. Use synthetic in-memory repos, local fake identity directories, local mock XRPC services, and small CAR fixtures. Do not use live network calls. Avoid large sleeps; use injected clocks, bounded channels, and Tokio test utilities where possible.

Test groups:

- Parser tests: raw `#commit`, `#sync`, `#account` preserve all sync 1.1 fields, including `prevData`, op `prev`, commit CID, CAR bytes, status, and time. Include malformed CBOR, missing required fields, wrong field types, null-vs-absent fields, and oversized payload boundaries.
- State store tests: load/save/delete chain and hosting state, replay handling, concurrent access for `MemStateStore`, and error propagation through a failing store implementation.
- MST inversion tests: golden create/update/delete chains, duplicate paths, missing `prev`, unknown actions, missing blocks, malformed CAR, and property-style cases using small random operation sequences.
- Verifier happy path tests: first sighting, chained commit, empty commit, missing record block with counter, and verified operations with record bytes.
- Verifier adversarial tests: rev replay, future rev, oversized commit, field mismatch, CAR root mismatch, missing commit block, malformed inner commit, bad signature with successful identity refresh, bad signature after refresh, duplicate path, op-CID mismatch, chain break, strict inversion failure, lenient inversion accept, legacy accept/reject, account inactive gate, and save-chain failure in policy-error mode.
- `#sync` tests: no-op fast path, malformed embedded CAR falling through to resync, field mismatch, signature failure, replay drop, full resync, and rev regression from `getRepo`.
- Resync worker tests: async queueing, pending replay, pending replay error delivery, buffer overflow, rate limiting, worker shutdown, and async error channel backpressure.
- Streaming integration tests: no-verifier behavior unchanged, verified happy path, verifier error flushes batch, account event gates following commit, per-DID ordering under parallelism, cross-DID concurrency, cursor watermark monotonicity, per-DID queue overflow, async resync event delivery, and async worker error delivery.
- Regression tests from atmos follow-ups: MST remove/height behavior, state serde/json shape if exposed, and no silent save failure during policy-error state advancement.

The full normal test suite should remain fast enough for local iteration. Any slow soak, fuzz, or large swarm tests should be opt-in rather than part of default `cargo nextest run --workspace --features full`.

## Commit Plan

Implementation commits should be organized roughly as:

1. Raw sync event parsing and public/private event shape.
2. `StateStore`, `MemStateStore`, state types, policies, typed errors, and stats.
3. CAR-to-block-store helpers and MST inversion.
4. Core `Verifier::verify_commit`.
5. `Verifier::verify_sync`, resync API, and full repo walking.
6. Account hosting tracking and gating.
7. Async resync worker and pending queue.
8. Streaming verifier integration.
9. Keyed scheduler and parallel streaming.
10. Docs, examples, doctests, and final cleanup.

Each behavioral commit should be test-first. Production code should not be added until the relevant failing test has been observed.
