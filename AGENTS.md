# Repository Guidelines

Shrike is a rust library for atproto that is correct, fast, robust, and easy to use.

See also https://atproto.com.

Shrike is heavily inspired by the atmos go library https://github.com/jcalabro/atmos.

The authoritative reference atproto implementation is the typescript code in https://github.com/bluesky-social/atproto.

## Project Structure & Module Organization

The library lives in `src/`, with feature-oriented modules such as `cbor/`, `identity/`, `repo/`, `sync/`, etc.

Generated lexicon bindings are under `src/api/`; do not edit files marked `Code generated by lexgen` by hand. We run `just update-lexicons && just lexgen` to update them.

Integration tests live in `tests/`, shared fixtures in `testdata/`, benchmarks in `benches/`, and fuzz targets in `fuzz/fuzz_targets/`. Workspace tools are in `tools/lexgen/` and `tools/shrike/`.

## Build, Test, and Development Commands

Use `just --list` to discover supported tasks. If Rust tooling is unavailable, enter the pinned Nix environment with `just dev`.

- `just build`: build the workspace with all features.
- `just test`: run unit and integration tests through `cargo nextest`.
- `just lint`: check formatting and run Clippy with warnings denied.
- `just check`: run the full build, lint, test, and doctest suite.
- `just shrike -- <args>`: run the CLI locally.
- `just fuzz 30`: fuzz each target for 30 seconds.
- `just update-lexicons`: fetch pinned upstream lexicons and atomically regenerate API code.
- `just lexgen`: regenerate from an existing local `lexicons/` cache.

## Coding Style & Naming Conventions

Avoid `unsafe`; workspace lints deny `unwrap`, `expect`, `panic`, and `unreachable` in production code. Keep feature dependencies aligned with the layered feature definitions in `Cargo.toml`.

Keep our code and documentation minimal and maintainable. Don't pull in new cargo dependencies without asking; we value having relatively few dependencies.

## Testing Guidelines

We must test rigorously and in-depth to ensure correctness and robustness (use unit tests, integration tests, end to end tests, fuzz tests, property tests, swarm tests as appropriate for the task at hand). Ensure that happy and sad paths are tested. However, do not add meaningless tests. Add regression tests for every bugfix.
